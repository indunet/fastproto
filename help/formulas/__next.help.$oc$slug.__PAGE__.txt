2:T29e0,<h1>Transformation Formulas</h1>
<p>A practical guide to transforming values during decode/encode.</p>
<h2>Overview</h2>
<p>Formulas let you convert between raw on‑wire values and engineering values. You can express them as inline lambdas or as classes implementing <code>java.util.function.Function</code>.</p>
<ul>
<li>Decode formula: raw -> target field type</li>
<li>Encode formula: target field type -> raw</li>
</ul>
<blockquote>
<p><strong>Note:</strong> Lambda formulas require annotation processing for compile-time code generation. The <code>fastproto</code> bundle includes this by default. For Android projects, see <a href="/help/android">Android guide</a> for setup details.</p>
</blockquote>
<h2>Quick Steps</h2>
<ol>
<li>Pick the field type and its data annotation (e.g., <code>@UInt32Type</code>).</li>
<li>Decide if a lambda is sufficient, or a reusable class is better.</li>
<li>Provide the correct input/output types for each direction.</li>
<li>Test round‑trip: value -> encode -> decode -> value.</li>
<li>Keep formulas pure (no side effects, deterministic).</li>
</ol>
<h2>Core Concepts</h2>
<h3>Direction &#x26; Types</h3>
<ul>
<li>Decode: <code>Function&#x3C;RawType, FieldType></code>
<ul>
<li>Example: <code>@UInt32Type</code> raw is <code>Long</code>; field may be <code>Double</code> (engineering).</li>
</ul>
</li>
<li>Encode: <code>Function&#x3C;FieldType, RawType></code>
<ul>
<li>Example: reverse the above conversion.</li>
</ul>
</li>
</ul>
<h3>Lambda vs Class</h3>
<ul>
<li>Lambda: <code>@DecodingFormula(lambda = "...")</code> / <code>@EncodingFormula(lambda = "...")</code> — included in <code>fastproto</code> bundle</li>
<li>Class: <code>@DecodingFormula(MyFunc.class)</code> / <code>@EncodingFormula(MyFunc.class)</code> where class implements <code>Function&#x3C;In, Out></code></li>
<li>Precedence: Class‑based formulas win if both lambda and class are present.</li>
</ul>

<h3>Lifecycle &#x26; Errors</h3>
<ul>
<li>Formulas are compiled/bound during graph resolve and invoked per field during decode/encode.</li>
<li>Throwing exceptions inside formulas will surface as <code>DecodingException</code> / <code>EncodingException</code> at call sites.</li>
</ul>

<h3>One‑way formulas</h3>
<ul>
<li>You may specify only one side if the other is identity, e.g., only <code>@DecodingFormula</code>.</li>
</ul>
<h2>Advanced</h2>
<ul>
<li>Constants &#x26; context: Prefer constructor parameters or class constants inside class‑based formulas; avoid hidden globals.</li>
<li>Composition: Split complex logic into smaller <code>Function</code> classes and delegate.</li>
<li>Performance: Lambdas are compiled once and reused; keep formulas simple and avoid heavy allocations in hot paths.</li>
<li>Validation: Add unit tests with known vectors; ensure symmetry if both directions are specified.</li>
</ul>
<h2>Best Practices &#x26; Troubleshooting</h2>
<ul>
<li>Ensure types match the codec direction (e.g., <code>UInt32</code> raw is <code>Long</code>).</li>
<li>Document non‑obvious conversions (units, offsets) near the field.</li>
<li>If results are off by a factor, verify integer vs floating arithmetic and cast points.</li>
<li>If exceptions bubble up, catch and wrap with clear messages in class‑based formulas to ease debugging.</li>
