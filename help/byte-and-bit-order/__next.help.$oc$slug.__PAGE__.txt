2:T2fc0,<h1>Byte &#x26; Bit Order</h1>
<p>A practical guide to endianness (byte order) and bit order, how they are applied in FastProto, and how to avoid common mistakes.</p>
<h2>Overview</h2>
<ul>
<li>Byte order controls how multi‑byte values are laid out in memory (e.g., UInt16/UInt32/UInt64, Int16/Int32/Int64).</li>
<li>Bit order controls how bit positions within a byte are interpreted by bit‑level annotations (e.g., <code>@BoolType</code>).</li>
<li>Set sensible defaults on the class, override per field only when needed.</li>
</ul>
<h2>Quick Steps</h2>
<ol>
<li>Check your protocol spec for endianness and bit numbering conventions.</li>
<li>Set class‑level defaults: <code>@DefaultByteOrder(...)</code>, <code>@DefaultBitOrder(...)</code>.</li>
<li>Add per‑field <code>byteOrder</code> only where the spec deviates from the default.</li>
<li>For bit flags, choose the <code>bitOrder</code> that matches the spec (<code>LSB_0</code> or <code>MSB_0</code>).</li>
<li>Validate with known vectors (round‑trip encode/decode tests).</li>
</ol>
<h2>Core Concepts</h2>
<h3>Byte Order</h3>
<ul>
<li>Global default: little‑endian.</li>
<li>Precedence: Field <code>byteOrder</code> > Class <code>@DefaultByteOrder</code> > Global default (LITTLE).</li>
<li>Affects only multi‑byte storage/reading; single‑byte types (<code>UInt8</code>, <code>Int8</code>, <code>Ascii/Char</code>) are unaffected.</li>
<li>Checksum note: <code>@Checksum.byteOrder</code> affects how the checksum value is stored/read; it does not change the calculation over the data range. See <a href="/help/checksum">Checksum / CRC</a>.</li>
</ul>
<h3>Bit Order</h3>
<ul>
<li>Global default: <code>LSB_0</code> (bit 0 is the least‑significant bit of the byte).</li>
<li>You can override at class level via <code>@DefaultBitOrder(...)</code> or per field via <code>bitOrder</code>.</li>
<li>Applies to bit‑level annotations like <code>@BoolType(byteOffset = x, bitOffset = y, bitOrder = ...)</code>.</li>
</ul>

<h2>Advanced</h2>
<ul>
<li>Network byte order is BIG‑endian; many industrial protocols mix endianness across fields—prefer class‑level defaults and minimal overrides.</li>
<li>Reverse addressing (fixed total length) does not change endianness—only index origin.</li>
<li>For checksums, the <code>byteOrder</code> only affects the stored checksum field’s byte order, not the CRC computation over data bytes.</li>
</ul>
<h2>Best Practices</h2>
<ul>
<li>Set class‑level defaults to reduce noise and mistakes.</li>
<li>Keep endianness consistent across related fields where possible.</li>
<li>Document any per‑field overrides with comments that reference the spec.</li>
<li>Add unit tests with known byte vectors to lock in expected ordering.</li>
