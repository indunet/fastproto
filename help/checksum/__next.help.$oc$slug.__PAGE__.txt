2:T33e9,<h1>Checksum / CRC</h1>
<p>A practical guide to defining and validating checksums in FastProto.</p>
<h2>Overview</h2>
<p>FastProto provides a single annotation <code>@Checksum</code> to describe:</p>
<ul>
<li>The data range to compute over</li>
<li>Where to store/read the checksum</li>
<li>Which algorithm and byte order to use for the stored value</li>
</ul>
<p>During encode, FastProto computes and writes the checksum automatically. During decode, it recomputes and validates.</p>
<h2>Quick Steps</h2>
<ol>
<li>Identify the data span: <code>start</code> (inclusive) and <code>length</code> (bytes).</li>
<li>Decide the storage location: <code>offset</code> where the checksum value resides.</li>
<li>Choose an algorithm <code>type</code> and value <code>byteOrder</code>.</li>
<li>Ensure the data span does not overlap the checksum storage bytes.</li>
</ol>
<h2>Core Concepts</h2>
<ul>
<li>Data range: <code>[start, start + length)</code> (checksum value itself is excluded).</li>
<li>Storage: <code>offset</code> points to the first byte of the checksum field.</li>
<li>Byte order: affects how the checksum value is written/read for multi‑byte types; it does not change the computation over the data bytes.</li>
<li>Width: implied by <code>type</code> (CRC8=1B, CRC16=2B, CRC32=4B, CRC64=8B).</li>
</ul>
<h2>Annotation</h2>

<ul>
<li><code>start</code>: start byte index (inclusive)</li>
<li><code>length</code>: number of bytes to include</li>
<li><code>offset</code>: where to write/read the checksum value</li>
<li><code>type</code>: algorithm, e.g. <code>CRC8</code>, <code>CRC8_SMBUS</code>, <code>CRC8_MAXIM</code>, <code>CRC16</code>, <code>CRC16_MODBUS</code>, <code>CRC16_CCITT</code>, <code>CRC32</code>, <code>CRC32C</code>, <code>CRC64_ECMA182</code>, <code>CRC64_ISO</code>, <code>XOR8</code>, <code>LRC8</code></li>
<li><code>byteOrder</code>: affects only how the checksum value is written/read (multi-byte), not the calculation</li>
</ul>

<h2>Best Practices</h2>
<ul>
<li>Keep <code>[start, start+length)</code> disjoint from the checksum storage bytes <code>[offset, offset+width)</code>.</li>
<li>Choose <code>byteOrder</code> to match the on‑wire representation of the checksum value.</li>
<li>Prefer a single <code>@Checksum</code> per checksum field; avoid overlapping ranges.</li>
<li>Add tests with known vectors to ensure both encode and decode paths are validated.</li>
</ul>
<h2>Troubleshooting</h2>
<ul>
<li>If decode throws <code>DecodingException</code>, recompute the expected checksum and compare against the stored bytes with the specified <code>byteOrder</code>.</li>
<li>Confirm the buffer is long enough to include the entire range and checksum field.</li>
